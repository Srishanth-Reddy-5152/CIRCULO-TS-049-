1. Executive Summary
CIRCULO is the working name for a 24-hour hackathon project aligned with SDG 12 — Responsible Consumption and Production. The project evolved from a simple campus item-sharing marketplace into a more differentiated concept: an AI-powered Sustainable Consumption Decision Engine. Its central question is: “Before you buy, what else could you do?”
The system is intended for a college/campus environment. A student describes a need in natural language. CIRCULO understands the need, searches available campus resources, identifies alternatives, and recommends the most practical lower-consumption option among borrowing, repairing, reusing, buying used, and finally buying new.

3. SDG 12 Alignment
The UN defines SDG 12 as ensuring sustainable consumption and production patterns. Relevant targets include efficient use of natural resources (12.2) and substantially reducing waste generation through prevention, reduction, recycling and reuse (12.5). These are directly relevant to CIRCULO's reuse-before-purchase model.
Official UN SDG 12 page: https://sdgs.un.org/goals/goal12
Official UN 2030 Agenda / Goal 12: https://sdgs.un.org/2030agenda
The strongest SDG framing for CIRCULO is not “we solve all waste.” It is: “We reduce unnecessary consumption by making underutilized resources visible and helping people choose reuse/repair/borrow options before a new purchase.”
4. How the Idea Evolved During the Discussion
4.1 Initial concept: campus sharing platform
The first proposal was a campus circular-consumption platform where students could list, discover, borrow, donate, repair, or reuse items such as textbooks, calculators, cables, chargers, lab components, tools, project materials and event supplies.
Core tagline proposed: “Before you buy. Check, borrow, reuse.”
Working name: CIRCULO.
Initial basic flow: list item → search item → request/borrow → return → impact dashboard.
Initial AI idea: semantic/product matching so a user can search by purpose rather than exact product name.
Initial dashboard idea: show reuse counts, purchases avoided, money saved, and estimated waste prevented.

4.3 Revised concept: Sustainable Consumption Decision Engine
The key strategic change is to make the platform about the decision immediately before consumption rather than about trading items.
Old framing: “Where can I get/buy this?”
New framing: “What is the most sustainable practical way to satisfy this need?”
Core question: “Do you need to buy anything at all?”
5. Core Problem Definition
5.1 Primary pain point
People make new purchases because they cannot easily discover existing resources around them. The problem is not necessarily a lack of resources; it is a lack of visibility into resources that are already owned, idle, repairable, or otherwise reusable.
Strong problem statement:
“People make new purchases because they cannot see or evaluate existing resources and sustainable alternatives around them.”
5.2 Three priority pain points
Invisible existing resources — “I need something, but I do not know whether someone around me already has it.”
No decision support — “I do not know whether I should borrow, repair, reuse, buy used, or buy new.”
Underutilized items — “I own something I do not use, but I do not have an easy way to make it useful to someone else.”
5.3 Secondary pain points
Users often describe a goal rather than a product name, so exact-keyword search is insufficient.
A campus may contain unused lab components, electronics, tools, books and event materials that are invisible to people who need them.
After a project, semester, event or exam, an item can become idle even though it still has useful life.
Sustainability messaging is often generic; users need decision-level feedback tied to their actual action.
Environmental impact estimates can become misleading if they are invented or presented as precise without a methodology.
6. Target Users
6.1 Seeker
Student who needs an item or capability.
Pain: cannot find an affordable, convenient, or sustainable way to satisfy the need.
Example: needs HDMI/projector connectivity, Arduino, calculator, lab component, textbook or tool.
6.2 Owner / Resource Provider
Student, lab, department or club with an underused item.
Pain: does not know who needs it and has little incentive/easy mechanism to expose it.
Can list, lend, donate, or mark an item as available for reuse.
6.3 Admin / Institution
Can view aggregate reuse activity and impact.
Can manage departments, labs, inventory, categories and potentially approvals.
7. The Core User Journey
User opens CIRCULO.
User describes a need in natural language.
AI/semantic matching identifies what the user is trying to accomplish.
System searches campus inventory and available peer-owned resources.
System identifies direct matches and compatible alternatives.
System evaluates possible actions: Borrow → Repair → Reuse → Buy Used → Buy New.
System ranks options by practicality, cost and sustainability.
User selects an option and submits a borrow/request/repair/reuse action.
Transaction is recorded.
Impact dashboard updates with transparent estimated metrics.
The experience should feel like a decision assistant, not a classifieds website.

10. AI / Intelligence Layer
10.1 Purpose
AI should solve a real matching problem: translate a human goal into possible products/solutions and match those solutions against campus inventory.
10.2 Recommended first implementation
Use semantic/product similarity rather than building a large custom model.
A lightweight TF-IDF + cosine similarity prototype can match terms such as “connect laptop to projector” to HDMI cable, USB-C-to-HDMI adapter, VGA adapter, etc.
If time permits, a small embedding-based semantic search layer can improve natural-language matching.
The UI can explain why an item was recommended rather than simply outputting a score.
10.3 What NOT to do
Do not add a generic chatbot merely to claim “AI-powered.”
Do not build a large custom ML model during a 24-hour hackathon.
Do not present fabricated CO2/waste savings as scientifically exact.

22. Unique Selling Proposition (USP)
“CIRCULO is not a campus marketplace. It is a sustainable consumption decision engine that converts a user’s need into the best available borrow, repair, reuse, used-buy, or new-buy option.”
23. What Makes the Revised Concept More Unique
Goal-based search rather than exact item search.
Decision support rather than only listings.
Explicit borrow → repair → reuse → used → new hierarchy.
Discovery of underutilized campus resources.
Idle Item Detector to proactively surface unused resources.
Impact feedback connected to actual reuse decisions.
Campus-first model creates a controlled environment suitable for a hackathon prototype.
24. Competitive / Novelty Caution
The conversation explicitly identified that generic campus swap/borrow/reuse platforms already exist. Therefore, do not claim that “students can exchange items on campus” is a novel invention. The novelty claim should focus on the combination of need understanding, sustainable option ranking, underutilized-resource discovery, and a reuse-before-purchase decision flow.
For the final hackathon pitch, perform a fresh competitor scan before making strong novelty claims. Existing implementations can be used to demonstrate that the general problem is real; the product differentiation should be stated narrowly and honestly.

27. Judge Questions to Prepare For
Likely question
Core answer
How is this different from a marketplace?
Marketplace behavior is not the core. CIRCULO starts from the user's need and recommends the most sustainable practical action before purchase.
Why AI?
Users describe goals in natural language. The system maps goals to products/alternatives and available resources.
Why would people list their items?
Campus identity, usefulness to peers, recognition/impact scores, and convenience can provide incentives; the prototype can simulate this.
How do you calculate impact?
Use a transparent prototype estimation methodology; never present demo assumptions as exact environmental facts.
Why a campus first?
A campus is a bounded community with repeat needs, known inventory sources, and manageable trust/logistics.
What happens if nothing is available?
The system can recommend used/new purchase as the fallback rather than pretending reuse is always possible.
Is this really SDG 12?
It directly supports sustainable consumption, resource efficiency, reuse and waste prevention, especially the spirit of Targets 12.2 and 12.5.
Can it scale?
The campus inventory model can expand to departments, multiple colleges, companies, co-working spaces or communities.

31. Product Principles
Sustainability must be actionable, not just informational.
AI must change a real decision, not merely decorate the UI.
Reuse should be the default recommendation when practical, not an absolute rule.
User convenience matters; sustainable options that are too difficult will not be adopted.
Transparency beats impressive-looking but unsupported environmental numbers.
The MVP should solve one journey extremely well.
32. Current Scope Decision
The current recommended direction is to proceed with CIRCULO, but NOT as a generic campus marketplace. The hackathon MVP should focus on three core problems: invisible existing resources, lack of decision support, and underutilized items.
The highest-priority feature is natural-language need → available/alternative solutions → sustainable action recommendation. Everything else is secondary.

41. Resource Rescue, Availability and Impact
41.1 Resource Rescue (Idle Item Detector)
Resource Rescue is the implementation of the Idle Item Detector from Section 13. Whenever an item is used or returned, update last_used. Compute idle_days = today − last_used. If idle_days exceeds 30, flag the item on a dashboard (e.g., ESP32 Dev Board, idle 42 days; Scientific Calculator, idle 63 days), each with a “Make Available” action. This adds a complete feature for very little code.

47. Integrated System Architecture
This section brings the website components, AI/matching layer, database, transaction lifecycle and impact reporting together into one implementation architecture. CIRCULO should be built as a modular monolith for the hackathon: one Streamlit application, Python service modules and a SQLite database. This minimizes integration overhead while keeping the logic separated enough for a three-member team.
47.1 Architecture Overview
CIRCULO has two entry paths that converge on the same Circular Decision Engine:
DEMAND — “I Need Something”: the user describes a goal or requirement.
SUPPLY — “I Have Something”: a student, laboratory, department or club lists a resource.
Need Understanding and Resource Understanding convert both inputs into structured categories, capabilities and constraints.
The Capability Graph connects needs to resources by what they can do, not only by exact product names.
The Circular Decision Engine compares practical routes such as borrow, repair, reuse, buy used and buy new.
The user sees a recommendation with its reasons and chooses an action.
The transaction service updates the resource lifecycle; the impact service records completed actions for the dashboard.
Figure 1. Integrated system architecture. Two entry paths (demand and supply) converge on one matching and decision engine; deterministic code owns transactions, data and impact.
Text equivalent of Figure 1: User → Streamlit UI → either “I Need Something” → Need Understanding, or “I Have Something” → Resource Understanding (the owner confirms suggested tags, then the listing is saved to SQLite) → Capability Graph + Matching Service (reads data/capabilities.json and the listed inventory in SQLite; filters out unavailable or incompatible items) → Circular Decision Engine (prototype weights: compatibility 40%, availability 25%, cost 15%, proximity 10%, circularity 10%; route order Borrow → Repair → Reuse → Buy Used → Buy New) → Recommendation + “Why this?” → User Action → Request & Transaction Service (deterministic code; AI never changes inventory state) → SQLite database → Impact Service → Impact Dashboard, which is shown on the Impact page of the UI.

48. End-to-End User Workflows
48.1 Workflow A — Find and Borrow a Resource
The student opens the Home page and selects “I Need Something.”
The student enters a natural-language need, for example: “I need a microcontroller with WiFi for my IoT project.”
Need Understanding extracts the likely category and required capabilities: microcontroller, WiFi and IoT.
The matching service searches resource names, descriptions, categories and capability tags.
The system filters out resources that are unavailable or incompatible with the request.
The Circular Decision Engine ranks the remaining options and compares sustainable routes where enough data exists.
The Results page shows the best option, alternatives, availability, estimated cost and a “Why this recommendation?” explanation.
The student selects “Request to Borrow.” The backend creates a PENDING request; it does not let AI change inventory state.
The owner or lab manager reviews the request and approves or rejects it.
On approval, the backend re-checks availability and creates the transaction/reservation. The resource is no longer available for competing approvals.
When the item is handed over, the transaction is marked BORROWED and the due date is recorded.
When the item is returned, the transaction becomes RETURNED and the item becomes AVAILABLE again.
The impact service records the completed reuse event according to the project's defined rules; the dashboard refreshes from the database.
48.2 Workflow B — List a Resource
The owner selects “I Have Something.”
The owner enters an item name and basic details such as condition, quantity, location and availability.
Resource Understanding suggests a category, capabilities and synonyms. For example, “Arduino Uno” may receive tags such as microcontroller, electronics, IoT and prototyping.
The owner confirms or edits the suggested tags; the system should not publish uncertain AI-generated information without confirmation.
The resource and its capability tags are saved to SQLite.
The item appears in the owner's My Resources page and becomes discoverable in searches if its availability permits.
48.3 Workflow C — Resource Rescue / Idle Item
The system finds eligible resources whose last_used date is older than the configurable prototype threshold.
The owner sees the item, its recorded idle duration and suggested actions: Keep, Make Available, Donate, Repair or Retire.
If the owner chooses Make Available, the resource listing and availability are updated.
Once listed, the item can be discovered by another student through the normal I Need flow.
Any later borrow/return activity is recorded through the standard transaction lifecycle.
48.4 Workflow D — Repair, Used and New Alternatives
These routes should be represented honestly according to what the prototype actually supports. Repair can use a simple repair-request status flow. Buy Used and Buy New can appear as comparison/fallback options with estimated prices or user-provided links, but the MVP does not need payment processing or a complete e-commerce checkout. Do not show fabricated listings, prices or environmental savings.

49. Transaction State and Data Flow
49.1 Separate Requests from Transactions
A request represents a user's intention to borrow. A transaction represents the actual approved resource movement. Keeping these separate makes rejected and cancelled requests auditable and avoids counting a request as a completed reuse event.
Entity
Purpose
Example statuses

PENDING, APPROVED, REJECTED, CANCELLED
Transaction
Actual loan lifecycle after approval/handover
BORROWED, RETURNED, OVERDUE, CANCELLED

Current inventory availability
AVAILABLE, RESERVED, BORROWED, UNAVAILABLE

REQUESTED, IN_REPAIR, REPAIRED, NOT_REPAIRABLE
49.2 Transaction Flow Diagram
Figure 2. Transaction state flow: the happy path, its exceptions, and the state of the request, item and transaction records after each step.
Text equivalent of Figure 2: (1) item AVAILABLE → (2) request created, status PENDING → (3) owner approves: request APPROVED, item RESERVED, transaction created with status RESERVED → (4) handover confirmed: item and transaction BORROWED, due date set → (5) item returned: transaction RETURNED, returned_at set, item AVAILABLE → (6) item AVAILABLE again, impact recorded once. Exceptions: the owner rejects or the student cancels, so the request becomes REJECTED or CANCELLED and the item stays AVAILABLE; a second approval of an item that is already RESERVED or BORROWED fails; if the due date passes without a return the transaction becomes OVERDUE until the item is returned.
49.3 Safe Approval Rules
Re-check current item availability immediately before approving a request.
Update request, item and transaction records together in a database transaction.
Do not allow an item to have two active borrow transactions at the same time.
Set returned_at only when the item is actually returned.
Record impact only once for the qualifying completed action; avoid duplicate dashboard counts.
Keep transaction and inventory updates in deterministic backend code, not AI-generated decisions.

56.2 Connection settings
PRAGMA foreign_keys = ON on every connection, because SQLite does not enforce foreign keys by default.
PRAGMA journal_mode = WAL to reduce locking when the app reads and writes during the demo.
One cached connection with check_same_thread=False, wrapped in st.cache_resource.
Parameterised queries (? placeholders) everywhere; never build SQL by string concatenation.
Status-changing operations run inside BEGIN IMMEDIATE ... COMMIT so two users cannot approve the same item at once.

56.4 SQL definition (db/schema.sql)
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  email TEXT NOT NULL UNIQUE,
  department TEXT,
  role TEXT NOT NULL DEFAULT 'student'
       CHECK (role IN ('student','lab','admin')),
  password_hash TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
 
CREATE TABLE categories (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL UNIQUE,
  parent_id INTEGER REFERENCES categories(id),
  synonyms TEXT
);
 
CREATE TABLE items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  owner_id INTEGER NOT NULL REFERENCES users(id),
  name TEXT NOT NULL,
  category_id INTEGER REFERENCES categories(id),
  description TEXT,
  condition TEXT CHECK (condition IN ('New','Good','Fair')),
  location TEXT,
  quantity INTEGER NOT NULL DEFAULT 1,
  quantity_available INTEGER NOT NULL DEFAULT 1,
  availability TEXT NOT NULL DEFAULT 'AVAILABLE'
       CHECK (availability IN
       ('AVAILABLE','RESERVED','BORROWED','UNAVAILABLE')),
  available_for TEXT NOT NULL DEFAULT 'borrow'
       CHECK (available_for IN ('borrow','donate','both')),
  available_until TEXT,
  last_used TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  CHECK (quantity_available BETWEEN 0 AND quantity)
);
 
CREATE TABLE item_capabilities (
  item_id INTEGER NOT NULL REFERENCES items(id),
  capability TEXT NOT NULL,
  PRIMARY KEY (item_id, capability)
);
 
CREATE TABLE need_queries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id),
  query_text TEXT NOT NULL,
  parsed_json TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
 
CREATE TABLE requests (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  requester_id INTEGER NOT NULL REFERENCES users(id),
  item_id INTEGER NOT NULL REFERENCES items(id),
  need_query_id INTEGER REFERENCES need_queries(id),
  status TEXT NOT NULL DEFAULT 'PENDING'
       CHECK (status IN
       ('PENDING','APPROVED','REJECTED','CANCELLED')),
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  decided_at TEXT
);
 
CREATE TABLE transactions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  request_id INTEGER NOT NULL UNIQUE REFERENCES requests(id),
  item_id INTEGER NOT NULL REFERENCES items(id),
  lender_id INTEGER NOT NULL REFERENCES users(id),
  borrower_id INTEGER NOT NULL REFERENCES users(id),
  start_date TEXT,
  due_date TEXT,
  returned_at TEXT,
  status TEXT NOT NULL DEFAULT 'RESERVED'
       CHECK (status IN
       ('RESERVED','BORROWED','RETURNED',
        'OVERDUE','CANCELLED')),
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
 
CREATE TABLE repairs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  item_id INTEGER NOT NULL REFERENCES items(id),
  issue TEXT,
  estimated_cost REAL,
  status TEXT NOT NULL DEFAULT 'REQUESTED'
       CHECK (status IN
       ('REQUESTED','IN_REPAIR','REPAIRED',
        'NOT_REPAIRABLE')),
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

56.5 Lifecycle and safe approval
Statuses and transitions are defined in Section 62.1. The approval step is the critical one. In a single database transaction, transaction_service re-checks that the item is AVAILABLE (or has quantity_available above zero), then marks the request APPROVED, creates the transaction as RESERVED, marks the item RESERVED and reduces quantity_available. If the check fails, nothing changes and the user sees a clear message. Handover, return and overdue marking are likewise single transactions. Because the database enforces CHECK (quantity_available BETWEEN 0 AND quantity) and the service uses BEGIN IMMEDIATE, an item can never be over-allocated. Impact events are inserted when a transaction reaches RETURNED, and the UNIQUE (transaction_id, metric_type) constraint prevents double counting.
56.6 Seed data
db/seed.py creates realistic but clearly demo campus data: about 10 users across CSE, ECE and other departments; 40 to 60 items (ESP32, Arduino Uno and Nano, Raspberry Pi, HDMI cable, USB-C to HDMI adapter, VGA adapter, calculators, textbooks, lab components) with their capabilities; a few completed transactions; and several items with old last_used dates so Resource Rescue has data to show.
56.7 Persistence on hosting
Treat Streamlit Community Cloud storage as ephemeral: files written at runtime may be lost when the app restarts. The app therefore rebuilds data/circulo.db from schema.sql and seed.py when the file is missing. If live persistent data is needed, the same schema moves to hosted Postgres (for example Supabase) and only db/database.py changes, because all SQL is kept behind the service modules.

57.3 Need understanding
Input: “I need a WiFi microcontroller for my IoT project.” Output, stored in need_queries.parsed_json:

}
 
Level 1 uses a keyword and synonym lookup against the capability vocabulary. If an LLM is configured, it is asked to return only this JSON shape; the response is validated, and on any error the keyword result is used, so the page never breaks.

57.6 Explanations, Resource Rescue and impact
“Why CIRCULO recommends this” lines are generated from the scoring inputs with no AI: for example “100% capability match”, “Available now”, “Free to borrow”, “Same department”, “Can be returned after your project”, “Avoids a new purchase”. A line appears only if the data supports it.
Resource Rescue (the Idle Item Detector of Section 13): idle_days = today − last_used. Items idle for more than the configurable threshold (default 30 days) are flagged, and the owner can choose Keep, Make Available, Donate, Repair or Retire.
Impact: figures come from impact_events. Savings are stored as estimates with a methodology note. No CO₂ or waste figure is shown unless a documented method backs it.

60. Testing, Security and Risk Register
60.1 Testing
Matching and scoring: the ESP32 example must return 100% and Arduino Uno and Nano 67%; Borrow must outrank Buy New when an item is available.
Manual end-to-end test of the MVP loop: need → results → request → approve → handover → return → impact updated.
Concurrency: two users requesting or being approved for the same single-unit item; the second approval must fail.
Impact: returning an item twice must not create duplicate impact events.
Failure cases: no search results, empty input, AI call failure, missing database file.
Freeze one hour before the deadline: no new features, only critical bug fixes.
60.2 Security and privacy (prototype level)
Parameterised SQL only; Streamlit escapes text it renders by default.
Passwords stored as salted hashes; demo accounts are clearly marked.
Role checks on owner-only and admin actions (approve, reject, hand over, mark returned).
Store only what is needed (name, email, department); there is no payment data.
Not production-hardened. Production use would add real authentication (for example college single sign-on), HTTPS-only hosting, audit logs and a hosted database.
