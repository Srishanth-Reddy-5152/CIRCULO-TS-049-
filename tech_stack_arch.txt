CIRCULO — Technology Stack & Website Architecture
Complete technical specification: languages, frameworks, database, AI layer, folder structure, page-by-page website design, deployment and risks
Companion to the CIRCULO SDG 12 Hackathon Project Dossier. The dossier defines what is being built and why; this document defines exactly what it is built with and how the pieces fit together. Where the two overlap (database, matching, screens), this document is the more detailed technical reference. Cost figures and sample data referred to here are demo assumptions and must be labeled as such in the prototype.

3. Frontend: Streamlit
3.1 Why Streamlit
The whole UI is written in Python, so the AI/matching member can call logic functions directly from the page code.
Built-in widgets cover everything needed: text areas, forms, selectboxes, buttons, metrics, tabs, columns, file/camera upload and charts.
Multipage navigation, session state and caching are built in.
Deployment is a push to GitHub.

3.3 Styling
Keep the default Streamlit theme with a small .streamlit/config.toml (primary colour green to signal sustainability, light background). Use a small amount of custom CSS through st.markdown only for result cards and the recommendation badge. Do not spend demo-critical hours on pixel-level design.

5. Database: SQLite
5.1 Decision
Database: SQLite, stored as a single file circulo.db in the project data/ folder. Access is through Python’s built-in sqlite3 module.
Reason
Detail
Zero setup
Ships with Python; nothing to install, host or configure.
Relational
Items, owners, transactions and capabilities are naturally relational (joins, foreign keys).
Fast enough
A campus demo has hundreds of rows, not millions.
Portable
Whole database is one file; copy it to restore a clean demo state.
Easy seeding
A seed.py script rebuilds the database with realistic campus data in seconds.
 
5.2 Connection settings
PRAGMA foreign_keys = ON on every connection, since SQLite does not enforce foreign keys by default.
PRAGMA journal_mode = WAL to reduce locking when the app reads and writes during the demo.
Open one cached connection with check_same_thread=False, wrapped in st.cache_resource.
Use parameterised queries (? placeholders) everywhere; never build SQL by string concatenation.

5.4 SQL definition
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  email TEXT NOT NULL UNIQUE,
  department TEXT,
  role TEXT NOT NULL DEFAULT 'student'
       CHECK (role IN ('student','lab','admin')),
  password_hash TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
 
CREATE TABLE categories (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL UNIQUE,
  parent_id INTEGER REFERENCES categories(id),
  synonyms TEXT
);
 
CREATE TABLE items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  owner_id INTEGER NOT NULL REFERENCES users(id),
  name TEXT NOT NULL,
  category_id INTEGER REFERENCES categories(id),
  description TEXT,
  condition TEXT CHECK (condition IN ('New','Good','Fair')),
  location TEXT,
  quantity INTEGER NOT NULL DEFAULT 1,
  quantity_available INTEGER NOT NULL DEFAULT 1,
  availability TEXT NOT NULL DEFAULT 'available'
       CHECK (availability IN
       ('available','requested','borrowed','unavailable')),
  available_for TEXT DEFAULT 'borrow',   -- borrow | donate | both
  available_until TEXT,
  last_used TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
 
CREATE TABLE item_capabilities (
  item_id INTEGER NOT NULL REFERENCES items(id),
  capability TEXT NOT NULL,
  PRIMARY KEY (item_id, capability)
);
 
CREATE TABLE requests (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id),
  item_id INTEGER REFERENCES items(id),
  description TEXT NOT NULL,
  parsed_json TEXT,
  status TEXT NOT NULL DEFAULT 'pending'
       CHECK (status IN
       ('pending','matched','fulfilled','cancelled')),
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
 
CREATE TABLE transactions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  item_id INTEGER NOT NULL REFERENCES items(id),
  owner_id INTEGER NOT NULL REFERENCES users(id),
  borrower_id INTEGER NOT NULL REFERENCES users(id),
  request_id INTEGER REFERENCES requests(id),
  start_date TEXT,
  due_date TEXT,
  returned_at TEXT,
  status TEXT NOT NULL DEFAULT 'requested'
       CHECK (status IN
       ('requested','approved','borrowed',
        'returned','rejected','overdue'))
);
 
CREATE TABLE repairs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  item_id INTEGER NOT NULL REFERENCES items(id),
  issue TEXT,
  estimated_cost REAL,
  status TEXT DEFAULT 'open'
);
 
CREATE TABLE impact_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER REFERENCES users(id),
  item_id INTEGER REFERENCES items(id),
  transaction_id INTEGER REFERENCES transactions(id),
  action TEXT NOT NULL,        -- borrow | repair | reuse | buy_used
  metric_type TEXT,
  estimated_saving REAL,
  methodology TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
 
CREATE TABLE price_reference (
  item_key TEXT PRIMARY KEY,
  repair_cost REAL,
  used_price REAL,
  new_price REAL,
  note TEXT DEFAULT 'demo data'
);

For listings with more than one unit (for example four ESP32 boards), availability changes only when quantity_available reaches zero. The status change and impact event are written in a single database transaction so the UI never shows an item as available when it is not.
5.6 Seed data
seed.py creates realistic campus data: about 10 demo users across CSE, ECE and other departments, 40–60 items (ESP32, Arduino Uno and Nano, Raspberry Pi, HDMI cable, USB-C to HDMI adapter, VGA adapter, calculators, textbooks, lab components), their capabilities, a few past transactions, and several items with old last_used dates so Resource Rescue has something to show. Seed data is clearly demo data.
5.7 Persistence on hosting
Streamlit Community Cloud storage should be treated as ephemeral: files written at runtime may be lost when the app restarts. For the hackathon, the app rebuilds circulo.db from seed.py when the file is missing. If persistent live data is needed, the same schema moves to a hosted Postgres service (for example Supabase) with only db.py changing. Keeping all SQL in db.py makes that swap small.
6. AI and Matching Layer
6.1 Build order: deterministic first
Level
Technique
Status
Level 1 (must have)
Keyword extraction + capability dictionary + capability overlap score
Always works offline; this is the demo baseline.
Level 2 (should have)
TF-IDF + cosine similarity (scikit-learn) over item names, descriptions, tags and capabilities
Lets “connect laptop to projector” reach HDMI cable and adapters.
Level 3 (optional)
LLM converts the request to structured JSON; falls back to Level 1 if the call fails
Better understanding of free-form need.
Level 4 (optional)
Small embedding model (for example sentence-transformers all-MiniLM-L6-v2) for semantic search
Only if the team is already comfortable; adds download size and load time.
Optional feature
Vision model for Scan & Identify
Photo → item name, category, capabilities; owner confirms.
 
6.2 Capability dictionary
A Python dictionary (or JSON file) maps item keys to capabilities, categories and tags. It is used both to structure new listings and to interpret needs.

    "tags": ["esp32","embedded","iot","electronics"]},
  "arduino uno": {
    "name": "Arduino Uno",
    "category": "Electronics > Development Board",

  "raspberry pi": {
    "name": "Raspberry Pi",

6.3 Need understanding
Input: “I need a WiFi microcontroller for my IoT project.” Output (stored in requests.parsed_json):
{
  "need": "microcontroller",
  "required_capabilities": ["wifi", "iot"],
  "purpose": "IoT project"
}
 
Level 1 uses a keyword and synonym lookup against the capability vocabulary. If an LLM is configured, it is asked to return only this JSON shape; the response is validated, and on any error the keyword result is used instead, so the page never breaks.
6.4 Matching and ranking
match_score = matched_capabilities / required_capabilities
Item
Capabilities matched
Match score
ESP32
microcontroller, wifi, iot (3 of 3)
100%
Arduino Uno
microcontroller, iot (2 of 3)
67%
Arduino Nano
microcontroller, iot (2 of 3)
67%
 
Where a requirement is a goal rather than a product (for example connecting a laptop to a projector), TF-IDF cosine similarity between the request text and each item’s text fields supplies the candidate list, and the capability score refines the order.
6.5 Circular decision engine
Factor
Weight
Notes
Compatibility
40%
Capability match score.
Availability
25%
Available now, quantity available, available_until.
Cost
15%
Borrow ₹0 scores highest; buy new lowest (sample prices from price_reference).
Proximity
10%
Same department or location scores higher.
Circularity
10%
Borrow > Repair > Reuse > Buy Used > Buy New.
 
score = compatibility × 0.40 + availability × 0.25 + cost_score × 0.15 + proximity × 0.10 + circularity × 0.10
These are prototype decision weights, not scientifically universal values. They live in a single config dictionary so they can be changed live and shown to judges. The routes evaluated are Borrow, Repair, Reuse, Buy Used and Buy New; Recycle/dispose is shown only for items at end of life.
6.6 Explanations
The “Why CIRCULO recommends this” list is generated from the scoring inputs, with no AI needed: for example “100% capability match”, “Available now”, “Free to borrow”, “Same department”, “Can be returned after your project”, “Avoids a new purchase”. Each line appears only if the underlying data supports it.
6.7 Resource Rescue and impact
Resource Rescue: idle_days = today − last_used; items idle more than 30 days are flagged with a Make Available action.
Impact: dashboard figures are aggregated from impact_events. Savings are stored as estimates with a methodology note. No CO₂ or waste figure is shown unless a documented method backs it.

13. Testing and Quality
Unit checks on the matcher and scoring: the ESP32 example must return 100%, Arduino Uno and Nano 67%, and Borrow must outrank Buy New when an item is available.
Manual end-to-end test of the MVP loop: need → results → decision → request → approve → return → impact updated.
Concurrency check: two users requesting the same single-unit item; the second must see it as unavailable.
Failure tests: no search results, empty input, AI call failure, database file missing.
Final freeze one hour before the deadline: no new features, only critical bug fixes.
14. Security and Privacy (Prototype Level)
Parameterised SQL only; Streamlit escapes text it renders by default.
Passwords stored as salted hashes; demo accounts clearly marked.
Role checks on admin and owner-only actions (approve, reject, mark returned).
Store only what is needed (name, email, department); no payment data exists in the system.
Prototype is not production-hardened; production use would add real authentication (for example college single sign-on), HTTPS-only hosting, audit logs and a hosted database.

18. Summary
CIRCULO is a Python application: a Streamlit multipage website on the front, plain Python service modules behind it, and a single SQLite database holding users, items, capabilities, requests, transactions, repairs and impact events. A deterministic capability dictionary and TF-IDF similarity understand and match needs, a weighted decision engine ranks Borrow, Repair, Buy Used and Buy New, and optional LLM and vision features sit on top with safe fallbacks. The whole system deploys from one GitHub repository and can be demonstrated from a laptop if the network fails.
